# Evaluation

Results of the offline evals, and what each change taught. How the evals work, and their trade-offs, is in [`ARCHITECTURE.md` §6](ARCHITECTURE.md#6-evaluation).

Three offline evals, run inside the `api` container. Results are committed as dated JSON under [`api/eval/results/`](../api/eval/results/).

```bash
docker compose exec api python -m app.eval.retrieval      # retrieval metrics
docker compose exec api python -m app.eval.chat           # LLM-judged chat answers
docker compose exec api python -m app.eval.faithfulness   # LLM-judged flashcards and quizzes
```

The eval set covers three deliberately different videos: a 56-minute university lecture, a 3-hour podcast, and a 10-minute programming tutorial. The golden set has 28 hand-reviewed questions, each with the time span where the video answers it, plus 6 adjacent questions the video *doesn't* answer and 12 broad whole-video questions ("What will I learn from this tutorial?"). Two of the 28 were added for the chat router ([#37](https://github.com/jdavidIP/grasp/issues/37)) and reuse another question's span. The current retrieval table uses all 28; the earlier comparisons below it were measured on the first 26.

## Retrieval

A retrieved chunk counts as a hit if it overlaps the golden time span. Production retrieves 8 candidates by hybrid search, then reranks down to 5.

| strategy | hit@1 | hit@3 | hit@5 | MRR |
|---|---|---|---|---|
| vector only | 0.82 | 1.00 | 1.00 | 0.90 |
| hybrid (vector + keyword, RRF) | 0.93 | 1.00 | 1.00 | 0.96 |
| **hybrid + LLM rerank** (production) | **0.96, 0.93** | **1.00** | **1.00** | **0.98, 0.96** |

(Two runs; one value means both runs agreed. [run1](../api/eval/results/retrieval-2026-10-02-seg-window-run1.json), [run2](../api/eval/results/retrieval-2026-10-02-seg-window-run2.json))

**Out-of-scope questions correctly declined: 5/6** in both runs (6/6 before the segment-window fix below; the miss is an answer-step bug it exposed, [#41](https://github.com/jdavidIP/grasp/issues/41); the out-of-scope set is now 12 questions, see [Chat answers](#chat-answers)).

The eval paid for itself on its first run. Keyword search used `plainto_tsquery`, which requires *every* term in the question to appear in a chunk. It matched nothing on 24 of the 26 questions, so "hybrid" search had silently been pure vector search. Switching to any-term matching raised hybrid + rerank hit@1 from **0.81 to 0.88** and MRR from **0.86 to 0.92**. A lecture question about the Marshall Plan, which no strategy had retrieved at any rank, went to rank 1: an exact name the embedding had flattened, which is the case hybrid search exists for. ([before](../api/eval/results/retrieval-2026-09-19.json) / [after](../api/eval/results/retrieval-2026-09-19-keyword-or.json))

The segmentation fix ([#15](https://github.com/jdavidIP/grasp/issues/15)) then cost some of that at rank 1. Chunks never cross topic boundaries, so better topics moved every chunk boundary, and production hit@1 went from 0.88 to 0.81 (identical across two runs) while hit@3 held at 0.96. I accepted the trade: every answer still reaches the chat model among the 5 reranked chunks, and the generation metrics below improved. ([results](../api/eval/results/retrieval-2026-09-19-segmentation.json))

**Chunk size ([#17](https://github.com/jdavidIP/grasp/issues/17)): 500 tokens diluted short answers, 250 mostly fixed it.** Both lecture questions no strategy retrieved at baseline had their answer sitting inside a ~500-token chunk that was mostly about something else. Halving `CHUNK_TARGET_TOKENS` to 250, reprocessing, and running the eval twice at each size: production hit@1 moved from a 0.81–0.85 range to 0.88–0.92, and MRR from 0.88–0.90 to 0.92–0.94 — ranges that don't overlap, so this isn't noise. The Marshall Plan question is now retrieved even by pure vector search (rank 4), a stronger fix than hybrid search's exact-name match. The other question still misses at every strategy: its answer sits inside a segment whose entire transcript is 167 tokens, already below the 250-token target, so there's no chunk left to split — that miss is a segmentation-boundary problem, not a chunk-size one. The cost: about 1.8x as many chunks to embed (the tutorial went from 6 to 11), and less transcript per chunk surviving into chat generation (5 reranked chunks now carry roughly half as much context). At 250 tokens, chat answers still score 1.00 faithful ([Chat answers](#chat-answers)), though there's no 500-token chat run to compare against. ([500-token: run1](../api/eval/results/retrieval-2026-09-23-chunk500-run1.json), [run2](../api/eval/results/retrieval-2026-09-23-chunk500-run2.json) / [250-token: run1](../api/eval/results/retrieval-2026-09-23-chunk250-run1.json), [run2](../api/eval/results/retrieval-2026-09-23-chunk250-run2.json))

**Segment boundaries ([#38](https://github.com/jdavidIP/grasp/issues/38)): the last miss was a boundary on a filler phrase.** That remaining lecture miss wasn't about chunk size. Segmentation compared each sentence-sized unit only with the next one, so a pause around "what's the word?" became its own three-word unit, scored as a topic change on both sides, and pulled the boundary ~30s off the real change. The answer ended up in a chunk mostly about the far right. It was a pattern, not a one-off: 6 of the lecture's 14 boundaries sat next to a unit of 4 words or fewer. Comparing 20s of speech on each side of a gap instead (chosen before measuring) halved those, and over two runs each, production hit@1 went from 0.89 and 0.86 to 0.96 and 0.93, hit@5 from 0.96 to 1.00, and MRR from 0.92 and 0.91 to 0.98 and 0.96. Every mode improved in aggregate, and besides the target, podcast `-06` moved from rank 3 and 2 to 1 and 1 under production retrieval (podcast `-01` dropped from rank 1 to 2 under vector and hybrid search, and under production in one run, and `-keyword-1` from 1 to 2 under vector search). It wasn't free: out-of-scope declines fell to 5/6, broad chat answers on the podcast scored 0.83 and 0.92 supported instead of 1.00 (partly judge error), specific ones 0.96 in one run ([run1](../api/eval/results/chat-2026-10-02-seg-window-run1.json), [run2](../api/eval/results/chat-2026-10-02-seg-window-run2.json)), and quizzes may have dipped (see Generation faithfulness). The cost is a coarser topic list in places (the lecture's far-right material is one 11-minute topic instead of five), which is fine for retrieval because each passage now sits in a chunk about it. ([before: run1](../api/eval/results/retrieval-2026-10-02-seg-baseline-run1.json), [run2](../api/eval/results/retrieval-2026-10-02-seg-baseline-run2.json))

## Chat answers

Every golden question goes through the production chat path, and gpt-4o judges the answer against the chunks or topic summaries the answer model actually saw ([#21](https://github.com/jdavidIP/grasp/issues/21)). Two runs, identical to two decimals:

| questions | n | supported | answers the question | declines | routed to the broad path |
|---|---|---|---|---|---|
| specific | 26 | 1.00 | 1.00 | — | — |
| broad | 6 | 1.00 | 1.00 | — | **0.50** |
| out-of-scope | 6 | 1.00 | — | 1.00 | — |

([run1](../api/eval/results/chat-2026-09-24-run1.json), [run2](../api/eval/results/chat-2026-09-24-run2.json))

- **The answer step isn't where chat loses quality.** Given the right sources, gpt-4o-mini answers faithfully and declines cleanly. With the score at the ceiling, a stronger answer model can't show a gain on this eval, so it stays gpt-4o-mini. Where chat does fail is upstream: retrieval (above) and routing.
- **Half the broad questions were routed wrong** in these runs. The router sent a question to the whole-video path if it contained a keyword ("summarize", "overview"), and asked an LLM classifier only when the question had no content word at all. "What will I learn from this tutorial?" has a content word, so it went down the specific path and got answered from 5 chunks. The judge still scored those answers as answering the question: it sees only the sources the answer saw, so it can't tell what a 5-chunk summary of a 3-hour podcast left out. The routing rate is the number that catches it.
- **Fix ([#37](https://github.com/jdavidIP/grasp/issues/37)): a gpt-4o-mini classifier routes every question, judging scope rather than wording.** Wording can't decide it either way: "Summarize what they said about James Randi" has the keyword but is about one topic. Dropping the heuristic with the classifier's original prompt made things worse: it called wide-ranging subject questions ("Why are functions used in programming?") broad, sending 0.32 and 0.29 of specific questions to the whole-video path. The prompt now asks whether answering needs the whole video or one part of it, and defaults to specific when unsure. With the broad set doubled to 12 so the fix isn't judged on the original 6, two runs each gave broad 0.92 and specific 0.00, and every specific and broad answer stayed supported and answering the question. One out-of-scope question in run 1 was answered instead of declined; it went down the specific path as it should, so the router didn't cause it, and the 09-28 baseline had a failure of the same kind. The classifier adds about 300 prompt tokens of gpt-4o-mini and one call's latency to every chat question. ([old prompt: run1](../api/eval/results/chat-2026-10-02-router-oldprompt-run1.json), [run2](../api/eval/results/chat-2026-10-02-router-oldprompt-run2.json) / [new prompt: run1](../api/eval/results/chat-2026-10-02-router-prompt-run1.json), [run2](../api/eval/results/chat-2026-10-02-router-prompt-run2.json))
- **Chat states a speaker slip as fact** ("the Soviet Union invaded Ukraine") in both runs. The #18 fix covered flashcards and quizzes, not the chat prompts ([#34](https://github.com/jdavidIP/grasp/issues/34)). The judge counts repeating the speaker as faithful, and didn't flag the slip in either run, so the eval's slip count can't be relied on for this.
- **Chat bridged neighbouring material to questions the video doesn't answer ([#41](https://github.com/jdavidIP/grasp/issues/41)).** Asked for file I/O best practices, the tutorial's try/except chunk came back as "a best practice for file I/O", flagged grounded, so the UI showed it with sources and no "Not covered" tag. The flag is what matters: when it's false the reader sees that tag. Six out-of-scope questions sitting next to a covered topic were added to the golden set before any prompt change (12 out-of-scope in total). On the old prompt, two of them bridged too (Gorbachev's reforms, on a lecture that never names him; the Maastricht Treaty). The specific-path prompt now says excerpts on a related topic are not an answer, and that a question about something they never mention isn't grounded. Asking each out-of-scope question 3 times per run, the flag was right on 33/36 and 34/36 asks, against 30/36 and 31/36 before. Maastricht went from 1 wrong in 6 asks to 0 in 8; file I/O from about half wrong (8 of 16 asks, including past eval runs) to 2 of 8. Specific answers stayed at 1.00 grounded, supported and answering the question in both chat eval runs. ([run1](../api/eval/results/chat-2026-10-22-adjacent-oos-run1.json), [run2](../api/eval/results/chat-2026-10-22-adjacent-oos-run2.json))
- **Two attempts to close the rest didn't hold, and aren't shipped.** Asking the model to quote its evidence first, with code checking the quote really is in the excerpts, made Gorbachev worse (grounded 10 of 10): it quoted real sentences about Soviet control slipping, which answer a different question. It also declined one real podcast answer ([run1](../api/eval/results/chat-2026-10-22-evidence-first-run1.json), [run2](../api/eval/results/chat-2026-10-22-evidence-first-run2.json)). A separate gpt-4o-mini grounding call was either strict enough to catch Gorbachev and declined 7 of 10 real lecture questions for "missing detail", or loose enough to answer those and missed Gorbachev 6 of 6.
- **A broad question asked after a specific one answered the earlier question again ([#48](https://github.com/jdavidIP/grasp/issues/48)).** "What Python concepts does this teach?", asked after a try/except question, came back as a try/except explanation. The chat eval sends every question with no history, so it can't see this. An ad-hoc probe (not kept in the repo) asked each of the 12 broad golden questions twice after one real specific exchange on the same video, and gpt-4o-mini labelled which question each answer responds to. Its flags were read by hand, because it also flags whole-video overviews that mention the earlier topic. Before the fix, 12/24 and 11/24 broad answers re-answered the earlier question; specific answers did so 0 times in 52. The history now comes labelled as already-answered context, followed by `Current question (answer this one)`, and both system prompts say to answer only the current question. After the fix, re-answers dropped to 2/24 in both runs, every one of them "Summarize this conversation", which can fairly mean the chat itself; specific stayed at 0/52. One answer in those probe runs came back as a JSON list instead of a string, which crashed the save and dropped the user's message; lists are now joined into paragraphs.
- **The first version of that fix moved the question to the end, after the sources, and it cost grounding.** It stopped the re-answers (0/24 twice) but made the answer model decline two answerable specific questions whose excerpts only partly state the answer: the Marshall Plan question, grounded in every earlier committed run, went to not grounded in both chat eval runs, and specific `grounded` fell to 0.96 and 0.93 while `faithful` stayed at 1.00, so the faithful score alone hid it ([run1](../api/eval/results/chat-2026-10-22-48-history-run1.json), [run2](../api/eval/results/chat-2026-10-22-48-history-run2.json)). It also declined all 12 out-of-scope questions in both runs, Gorbachev included — the same strictness that cost the real answers; counting wrong `grounded` flags, question-last made 1 and 2 per run against 0 and 1 for question-first. Holding the excerpts fixed and asking each of the 28 specific questions 3 times, question-last was grounded 80/84 in both runs against 84/84 for the old order; the history label and instruction alone were 84/84 and 83/84. With the question back before the sources, specific `grounded` returned to 1.00 in both chat eval runs, every check stayed at 1.00 for specific and broad, and out-of-scope declined 0.92 in both (0.83 before), the one miss each time being Gorbachev from #41 ([run1](../api/eval/results/chat-2026-10-22-48-question-first-run1.json), [run2](../api/eval/results/chat-2026-10-22-48-question-first-run2.json)).
- **Specific answers listed all 5 reranked excerpts, whether the answer used them or not ([#47](https://github.com/jdavidIP/grasp/issues/47)).** Checking an answer meant clicking through sources that were sometimes unrelated. The answer model now returns `used_excerpts`, the excerpts it states something from, and only those are listed; a grounded answer that names none is shown as not covered. Over two chat eval runs, specific answers list 1.75 and 1.82 sources on average (13 of 28 list one), every check stayed at 1.00 for specific and broad, out-of-scope declined 0.92 in both as before, no answer was flipped to not covered, and the model never left the list out. The used excerpts still overlap the golden span in 27 of 28 and 28 of 28 questions whose retrieved excerpts did; the one miss is a podcast question the video answers in two places, and the excerpts listed state the answer more directly than the golden one. The no-source rule didn't catch Gorbachev (#41): the answer did use an excerpt, it just over-reached from it. ([run1](../api/eval/results/chat-2026-10-25-used-sources-run1.json), [run2](../api/eval/results/chat-2026-10-25-used-sources-run2.json))
- **Per-sentence citation markers were tried first and dropped.** The model marked each sentence with an excerpt number, and a marker was kept only if the sentence's embedding was close enough to its chunk's. On 168 (sentence, chunk) pairs labelled by gpt-4o, only 48% of specific and 22% of broad markers pointed at a moment that states the sentence, and similarity couldn't tell them apart: most wrong markers pointed at the right part of the video while the sentence added something not said there. Reaching 90% correct markers kept 2 of 44 good specific ones. ([labels](../api/eval/results/citation-labels-2026-10-25-both-runs.json), [design notes](superpowers/specs/2026-10-25-chat-used-sources-design.md))
- Reading the judge's reasons caught a bug in the judge itself before these runs: it marked a plain "the video doesn't cover this" as an unsupported claim.

## Cost per feature

The LLM wrapper totals tokens per model while an eval runs, so each feature's cost is measured rather than estimated. gpt-4o-mini tokens per request (prompt + completion), across two runs:

| request | gpt-4o-mini tokens | calls |
|---|---|---|
| chat, specific question | 3,460 / 3,450 | 2 (rerank, answer) |
| flashcard deck, 10 cards, whole video | 15,600 / 17,400 | 8–9 |
| quiz, 10 questions, whole video | 20,800 / 30,100 | 10–13 |

Embeddings add under 3% on top. The quiz spread is the top-up: when validation leaves a quiz short, it generates once more for the shortfall, which run 2 needed. The gpt-4o judge is eval-only: it uses about half to two-thirds as many tokens as what it judges, at gpt-4o's higher price. ([faithfulness run1](../api/eval/results/faithfulness-2026-09-24-usage-run1.json), [run2](../api/eval/results/faithfulness-2026-09-24-usage-run2.json))

## Generation faithfulness

gpt-4o judges every generated flashcard and quiz question against the raw transcript of the segment it cites. It uses a different model from the gpt-4o-mini generator, so the generator isn't grading itself. The table shows what users see, meaning the items that survive the pipeline's own validation pass; the per-run results files also report the raw candidates and the rejected ones.

| | Phase 7 baseline (1 run) | now (2 runs) |
|---|---|---|
| quiz questions: answer key correct | 0.80 | 0.97, 1.00 |
| quiz questions shipped, of 30 requested | 30 | 30, 30 |
| flashcards: faithful | 0.81 | 0.87, 0.93 |
| flashcards shipped, of 30 requested | 27 | 30, 30 |

Single runs on about 30 items are noisy: *identical* code scored 0.71 and 0.87 on quiz key correctness. So every change below was judged on at least two runs, and the per-run results are all committed under [`api/eval/results/`](../api/eval/results/). The judge's per-item reasoning is in each results file. What it shows:

- **The validators were checking against the wrong context, and one run made that look fixed.** After the segmentation fix ([#15](https://github.com/jdavidIP/grasp/issues/15)) a single run showed shipped flashcards scoring above raw output, so the flashcard validator looked net-useful. Three more runs said otherwise. In the two cleanest, it rejected 11 and 14 cards, of which 11 and 12 were faithful, and shipped decks of 23 and 21 of 30; the third pointed the same way. The cause, for both flashcards and quizzes, was that each validator checked items against the same summary-plus-two-excerpts context the generator had seen. It couldn't verify items grounded elsewhere in a topic (so it rejected good ones), and it couldn't tell a fact stated in the video from one the generator filled in from general knowledge (so it kept bad ones).
- **Fix ([#16](https://github.com/jdavidIP/grasp/issues/16)): validate each item against the full transcript of the segment it cites,** one call per cited segment, in parallel. By my token estimate it costs about the same, because only cited segments are sent. Per-feature cost is now measured ([#21](https://github.com/jdavidIP/grasp/issues/21), see [Cost per feature](#cost-per-feature)), but validation is counted together with generation, so the old-versus-new validator comparison is still an estimate. Wrongly rejected cards fell from 11 and 12 per run to between 0 and 2 across the four runs since, and quiz answer keys went from about 0.81 (the mean of three runs after the segmentation fix: 0.86, 0.71, 0.87) to 0.93. The 0.80 baseline above also includes the segmentation fix's gain. The validator now discriminates: rejected quiz questions score 0.54 and 0.62 faithful against 0.93 for the ones shipped. Two prompt changes went with it (keyed claims must be stated, not inferred; true/false statements must restate or be contradicted by the video), but by themselves they didn't move the overall number outside noise.
- **A stricter validator ships shorter quizzes, so it tops up.** A 10-question podcast quiz came back with 7, 9, 10 and 5 questions across four runs. If validation leaves a quiz short, it now generates once more for just the shortfall, validates it the same way, and stops (`TOP_UP_ROUNDS = 1`). Both runs then shipped the full 30. On longer videos that roughly doubles the generation calls, all on gpt-4o-mini.
- **What's left:** about 2 in 30 shipped quiz questions still have a debatable key, mostly multi-select questions where a distractor is arguably true. Shipped flashcard faithfulness is 0.83-0.93 across four runs, within noise of before: the flashcard fix restored full decks and stopped false rejections, but it didn't measurably make cards more faithful. Grading is deterministic, so a bad key marks a correct answer wrong.
- **The segment-window fix ([#38](https://github.com/jdavidIP/grasp/issues/38)) may have cost quizzes a little.** Shipped quiz faithfulness averaged 0.92 over four runs on the new segments (0.87, 0.93, 0.90, 0.97) against 0.97 over six runs on the old segments with the same generation code ([09-23](../api/eval/results/faithfulness-2026-09-23-speaker-slips.json), [09-23 run2](../api/eval/results/faithfulness-2026-09-23-speaker-slips-run2.json), [09-24 run1](../api/eval/results/faithfulness-2026-09-24-usage-run1.json), [run2](../api/eval/results/faithfulness-2026-09-24-usage-run2.json), and the two baseline runs linked below). That's within noise: the old runs ranged 0.93–1.00, and three of the four new runs fall at or below that range's bottom. Shipped flashcards were unchanged (0.90 vs 0.88). The obvious suspect, longer segments getting the same 2 excerpts, doesn't hold up. Generated quiz candidates do fail more on longer segments: 0.15 on segments the generator sees in full (1–2 chunks), 0.20 on 3–6 chunks, and 0.24 on 7+ chunks. But the validator removes that difference: among shipped items the rates are 0.08, 0.10 and 0.05, with no length trend. So excerpt selection stays as it is: thin coverage costs extra rejected candidates, not worse shipped quizzes. ([baseline run1](../api/eval/results/faithfulness-2026-10-02-seg-baseline-run1.json), [run2](../api/eval/results/faithfulness-2026-10-02-seg-baseline-run2.json) / [new segments run1](../api/eval/results/faithfulness-2026-10-02-seg-window-run1.json), [run2](../api/eval/results/faithfulness-2026-10-02-seg-window-run2.json), [run3](../api/eval/results/faithfulness-2026-10-03-seg-window-run3.json), [run4](../api/eval/results/faithfulness-2026-10-03-seg-window-run4.json))
- **True/false statements made false by a qualifier word ([#54](https://github.com/jdavidIP/grasp/issues/54)).** "Odysseus took *only* a year with Circe" was keyed False, though the video says a whole year: the fact matched and only "only" made it false, so a careful viewer was marked wrong. The ban on manufacturing wrong answers with absolute words covered multiple-choice distractors but not true/false, and the validator counted "only" vs "a whole year" as a contradiction. Generation now has to change a fact, never a degree, and the validator rejects statements and options that are wrong only because of a qualifier. Measured with an ad-hoc cheap check, a throwaway script not kept in the repo (true/false-only quizzes, 3 per video, gpt-4o-mini classifying each false statement as fact- or qualifier-keyed), qualifier-keyed false statements fell from 15/79 and 11/70 to 8/82 and 5/79 over two runs each. The lecture and tutorial reached 0 in the second run; what's left is on the podcast, statements about a speaker's views ("the speaker believes logic alone is sufficient"). The gain is almost all generation: the validator still passes most qualifier-keyed statements it's shown. Shipped quiz faithfulness was 0.80 and 0.97, against the 0.87–0.97 range above. The 0.80 run's six misses include three where the judge's own reason agrees with the key, and one podcast statement of the kind still left ("the Pentagon has confirmed that all videos…"). Shipped flashcards scored 1.00 and 0.77; the 0.77 is below the 0.83–0.93 range under "What's left", but this change doesn't touch flashcard generation, so it's almost certainly run-to-run noise. ([run1](../api/eval/results/faithfulness-2026-10-22-tf-qualifier-run1.json), [run2](../api/eval/results/faithfulness-2026-10-22-tf-qualifier-run2.json))
- **A gpt-4o validator isn't worth it: the validator stays gpt-4o-mini ([#35](https://github.com/jdavidIP/grasp/issues/35)).** Two runs each with gpt-4o-mini and gpt-4o as the validation pass (generation stayed on gpt-4o-mini). Unfaithful items shipped, out of about 30: flashcards 2 and 4 on mini against 2 and 2 on gpt-4o, quizzes 3 and 1 against 1 and 1. That is 1–2 items, inside the run-to-run noise of about ±4–5 items at this size, so it doesn't clear the bar for switching. gpt-4o caught more of the bad quiz questions (5 of 6 and 3 of 4 against 3 of 6 and 2 of 3) but was stricter on good ones: it rejected 11 quiz candidates in both runs against 7 and 5, and 6 and 8 of those were faithful against 4 and 3 on mini, which costs extra over-generation. The judge is also gpt-4o, so some of its agreement with a gpt-4o validator is a model agreeing with itself, which flatters it. On cost, the validator reads about 81–85k prompt tokens per run (the gpt-4o rows under flashcards and quizzes, since only validation uses gpt-4o there): about $0.21 on gpt-4o against about $0.01 on mini, or roughly $0.035 against $0.002 per generated deck or quiz. That is about 15 times the price for a gain I can't separate from noise. The validator model is now `llm.VALIDATION_MODEL`, and `python -m app.eval.faithfulness --validator-model` swaps it per run. The counts above come from an ad-hoc script over the per-item judgments, not kept in the repo. ([mini run1](../api/eval/results/faithfulness-2026-10-24-validator-gpt-4o-mini-run1.json), [run2](../api/eval/results/faithfulness-2026-10-24-validator-gpt-4o-mini-run2.json) / [gpt-4o run1](../api/eval/results/faithfulness-2026-10-24-validator-gpt-4o-run1.json), [run2](../api/eval/results/faithfulness-2026-10-24-validator-gpt-4o-run2.json))
- **Fix ([#18](https://github.com/jdavidIP/grasp/issues/18)): don't state a speaker slip as fact, and don't silently correct it either.** Speakers misspeak and captions mishear (the tutorial's "angle brackets" for Python lists), and generation previously repeated whatever was said as literal truth. It's now told to avoid a slip-dependent item when it can, and otherwise state the corrected fact while naming the slip — a `note` column for flashcards, folded into the existing `explanation` for quizzes; the validators and the eval judge were all updated with the matching exception, or they'd reject a correctly-noted item as invented. Two eval runs found **zero of the three known slips stated as fact across 148 sampled items**. Both runs happened to sample zero items touching those exact facts at all — whole-video scope spreads 10 kept items across every topic, so one specific fact isn't guaranteed a hit — so the automated eval confirms the safety property but not reliably the note-writing itself; a deliberate topic-scoped test against the real slip confirmed that part directly, producing the exact note the prompt asks for.

## Known limitations

- **Segmentation is reviewed by hand, not scored.** Reviewing the eval videos is how the auto-caption bug was found (the 3-hour podcast had become 4 topics; it's now 22). Whole-video generation still gives every topic the same 2 excerpts, so the podcast's longest topic (26 minutes, 22 chunks) is only ~9% represented. This is a known limit, deferred until an eval shows it hurts ([#15](https://github.com/jdavidIP/grasp/issues/15)).
- **Small eval set.** 26–28 retrieval questions and about 30 judged items per group give directional numbers, not precise ones. At 250 tokens per chunk, the tutorial has only 11 chunks, so @5 and @8 saturate for short videos. hit@1 and MRR are the metrics that separate strategies.
- **The router still misses some phrasings.** "What Python concepts does this teach?" goes down the specific path in every run; naming a field makes the classifier read it as a question about that subject. The prompt wasn't tuned to that one phrasing, so others like it will miss too. 12 broad questions are still a small sample, and the classifier sees the question without the conversation, so a follow-up like "tell me more" is routed on its own words.
- **Some boundaries still land on noise.** The windowed comparison halved boundaries next to filler units but didn't remove them: one lecture topic starts at "(student speaking faintly)". Short real sub-topics can also be folded into a neighbour ([#38](https://github.com/jdavidIP/grasp/issues/38)).
- **The note isn't reliably written even when the correction is.** Generation is told to state the corrected fact for a speaker slip *and* name it in a note. In manual testing both halves fired together under topic scope (full segment context), but whole-video scope's thinner context (the same 2-excerpts-per-topic limit noted above) sometimes stated the correction with no note. The eval confirms no slip is stated as fact; it doesn't yet confirm the note appears whenever it should ([#18](https://github.com/jdavidIP/grasp/issues/18)).
- **A false true/false statement can still exaggerate a speaker's stated view.** On opinion-heavy content, a statement like "the speaker believes logic *alone* is sufficient" can pass validation when the speaker only said logic is overrated. It's the qualifier problem from [#54](https://github.com/jdavidIP/grasp/issues/54), applied to opinions: about 3 of the 161 false statements in the #54 check, all on the podcast. Questions about what a speaker actually argues are fine and wanted. The likely fix is to make the generator quote the line that contradicts each false statement, but at this rate a measurable improvement would take many judged runs. The golden set also has only one podcast, and nothing as argument-driven as a political show.
- **Chat can still mark a near-miss answer as grounded.** When a question names something the video never mentions, attached to a topic it does cover, the flag is still wrong some of the time: Gorbachev's reforms in 5 of 8 asks, file I/O best practices in 2 of 8. The answer text usually admits the gap, but without the "Not covered" tag the sources make it look grounded. Checking the name in code would fail on auto-caption misspellings (the lecture's captions say "Billy Braun" for Willy Brandt); a stronger model for the grounding decision is the likely next step, weighed with [#35](https://github.com/jdavidIP/grasp/issues/35) ([#41](https://github.com/jdavidIP/grasp/issues/41)).
- **The judge is an LLM.** It follows a strict rubric and writes its reasoning before each verdict, but it still makes mistakes. For example, it treated a caption mishearing ("accept" for `except`) as a speaker slip.
